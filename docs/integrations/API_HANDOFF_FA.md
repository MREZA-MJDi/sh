# قرارداد تحویل وب‌سرویس‌های آکادمی شیخان

## وضعیت فعلی

منطق دامنه و جریان‌های داخلی شیخان پیاده‌سازی شده‌اند، اما هیچ API واقعی برای SpotPlayer یا Quiz24 در این مخزن تحویل نشده است. بنابراین:

- هیچ URL، مسیر، هدر احراز هویت یا payload خارجی حدس زده نشده است.
- Gateway پیش‌فرض هر دو سرویس در وضعیت \`contract_missing\` است و درخواست شبکه ارسال نمی‌کند.
- درخواست‌های مدیریتی در جدول \`integration_runs\` با وضعیت \`waiting_contract\` ذخیره می‌شوند.
- وضعیت دوره، آزمون، ویدیو یا لایسنس فقط پس از پاسخ معتبر سرویس خارجی به وضعیت موفق تغییر می‌کند.
- کلیدهای سرویس در دیتابیس با Eloquent encrypted cast نگهداری می‌شوند و نباید وارد log شوند.

برای فعال‌سازی واقعی، کارفرما باید اطلاعات بخش‌های بعد را از ارائه‌دهنده سرویس دریافت و تحویل تیم فنی کند.

---

## ۱. جریان ساخت دوره و دسترسی آموزشی

### ساخت دوره در شیخان

فرم مدیریت دوره یک رکورد محلی در جدول \`courses\` می‌سازد. اطلاعات اصلی:

| فیلد | توضیح |
|---|---|
| \`title\` | نام دوره |
| \`type\` | رایگان یا پولی |
| \`price\` | مبلغ تومان؛ برای دوره رایگان صفر |
| \`delivery_type\` | SpotPlayer، اسکای‌روم یا حضوری |
| \`teacher_id\` | مدرس مسئول |
| \`spotplayer_course_id\` | شناسه دوره متناظر در SpotPlayer، پس از ایجاد/ثبت در سرویس |
| \`status\` | پیش‌نویس، منتشرشده یا بایگانی |

**نکته مهم:** ساخت دوره در شیخان با ساخت دوره در پنل SpotPlayer یک عملیات نیست. باید از کارفرما مشخص شود SpotPlayer API رسمی برای ایجاد Course دارد یا خیر.

- اگر API ایجاد دوره دارد، Adapter باید عملیات ایجاد دوره را انجام دهد و شناسه خارجی را برگرداند.
- اگر API ایجاد دوره ندارد، اپراتور دوره را در پنل SpotPlayer می‌سازد و External Course ID را در شیخان ثبت می‌کند.
- در هر دو حالت، شناسه تا زمان بررسی API معتبر فرض نمی‌شود و وضعیت دوره \`awaiting_api_verification\` باقی می‌ماند.

### دسترسی دانش‌آموز به دوره

منطق داخلی دسترسی در \`CourseEnrollmentService\` قرار دارد:

1. عضویت دانش‌آموز در کلاس مرتبط با یک دوره رایگان منتشرشده، دسترسی فعال ایجاد می‌کند.
2. عضویت در کلاس دوره پولی به‌تنهایی دسترسی پولی ایجاد نمی‌کند؛ وضعیت آن \`pending_payment\` است.
3. دسترسی دوره پولی فقط پس از Callback معتبر و تأییدشده درگاه پرداخت باید از متد \`grantAfterVerifiedPayment\` فعال شود.
4. صدور لایسنس فقط برای دانش‌آموز فعال، دوره منتشرشده، دوره SpotPlayer و Enrollment فعال مجاز است.
5. برای یک ترکیب دانش‌آموز/دوره، درخواست تکراری لایسنس دوباره ثبت نمی‌شود؛ مگر بعد از شکست یا ابطال و درخواست جدید.

در این نسخه، درگاه پرداخت به این جریان متصل نشده است؛ کارفرما باید قرارداد Callback پرداخت را جداگانه تحویل دهد.

## ۲. قرارداد موردنیاز SpotPlayer

پیاده‌سازی داخلی در این مسیر قرار دارد:

- \`App\\Services\\SpotPlayer\\Contracts\\SpotPlayerGateway\`
- \`App\\Services\\SpotPlayer\\SpotPlayerService\`
- \`App\\Services\\SpotPlayer\\UnavailableSpotPlayerGateway\`

Gateway آینده باید DTO داخلی را به قرارداد واقعی SpotPlayer تبدیل کند. برای پیاده‌سازی Adapter، موارد زیر از کارفرما/پشتیبانی SpotPlayer دریافت شود.

### اطلاعات اتصال

| مورد | اطلاعات لازم |
|---|---|
| Base URL | آدرس رسمی محیط تست و عملیاتی |
| Authentication | نام هدر دقیق، نام پارامتر، پیشوند Token و روش امضا |
| API Key | کلید مجزا برای Sandbox و Production |
| TLS | گواهی معتبر؛ ارتباط بدون بررسی SSL مجاز نیست |
| API version | نسخه و تاریخ اعتبار مستندات |
| Rate limit | سقف درخواست در دقیقه و Headerهای اعلام محدودیت |
| IP allowlist | در صورت نیاز، IP سرور شیخان |
| Support | راه تماس برای خطاهای 401، 403 و خطاهای سمت سرویس |

### عملیات موردنیاز

| عملیات تجاری | انتظار از API |
|---|---|
| بررسی اتصال | اعتبارسنجی کلید و دسترسی حساب |
| فهرست دوره‌ها | External Course ID، عنوان و وضعیت |
| جزئیات دوره | بررسی وجود و فعال‌بودن Course ID |
| ایجاد دوره | در صورت پشتیبانی؛ دریافت External Course ID |
| ثبت/آپلود ویدیو | روش آپلود، تکمیل پردازش و دریافت Video ID |
| صدور لایسنس | اتصال دانش‌آموز به یک یا چند External Course ID |
| دریافت لایسنس | شناسه، وضعیت، تاریخ صدور و محدودیت دستگاه |
| ابطال لایسنس | ابطال قطعی با شناسه خارجی و دریافت نتیجه |
| تست وضعیت | تفکیک لایسنس فعال، معلق، منقضی و باطل |

### داده موردنیاز برای صدور لایسنس

فرمان داخلی شیخان در \`SpotPlayerLicenseCommand\` این اطلاعات را در اختیار Adapter قرار می‌دهد:

\`\`\`json
{
  "idempotency_key": "shikhan-license-unique-key",
  "student_reference": "internal-student-reference",
  "student_name": "نام دانش‌آموز",
  "external_course_id": "COURSE-ID-FROM-PROVIDER",
  "watermark_text": "0912xxxxxxx",
  "device_limits": {
    "total": 2,
    "windows": 2,
    "macos": 2,
    "ubuntu": 2,
    "android": 2,
    "ios": 2,
    "web": 2
  },
  "expires_at": null
}
\`\`\`

ارائه‌دهنده باید روشن کند که محدودیت دستگاه «تعداد کل دستگاه» است یا محدودیت جداگانه برای هر پلتفرم. مقدارهای نمونه بالا قرارداد قطعی SpotPlayer نیستند و صرفاً شکل داده داخلی شیخان را نشان می‌دهند.

### پاسخ مورد انتظار از صدور لایسنس

Adapter باید پاسخ اصلی ارائه‌دهنده را به مدل داخلی زیر تبدیل کند:

\`\`\`json
{
  "external_license_id": "PROVIDER-LICENSE-ID",
  "license_key": "LICENSE-KEY",
  "secure_download_url": "https://provider.example/secure-license",
  "status": "active",
  "issued_at": "2026-11-10T10:30:00Z"
}
\`\`\`

این پاسخ نمونه قرارداد داخلی است، نه ادعای ساختار واقعی پاسخ SpotPlayer. وضعیت محلی فقط وقتی \`active\` می‌شود که شناسه، کلید و URL معتبر از سرویس دریافت و اعتبارسنجی شده باشند.

### واترمارک و سیاست دستگاه

کارفرما باید مشخص کند:

- آیا شماره موبایل دانش‌آموز باید در واترمارک نمایش داده شود؟
- متن واترمارک در کدام فیلد و با چه محدودیت طولی ارسال می‌شود؟
- آیا محدودیت دستگاه بعد از ابطال و صدور مجدد پاک می‌شود؟
- آیا حذف یک دستگاه توسط دانش‌آموز امکان‌پذیر است؟
- آیا لایسنس تاریخ انقضا دارد؟
- آیا محیط Test لایسنس غیرقابل‌استفاده در Production صادر می‌کند؟

## ۳. قرارداد موردنیاز Quiz24

پیاده‌سازی داخلی در این مسیر قرار دارد:

- \`App\\Services\\Quiz24\\Contracts\\Quiz24Gateway\`
- \`App\\Services\\Quiz24\\Quiz24Service\`
- \`App\\Services\\Quiz24\\Quiz24ResultImporter\`
- \`App\\Services\\Quiz24\\UnavailableQuiz24Gateway\`

### اطلاعات اتصال

کارفرما باید Base URL، نسخه API، روش احراز هویت، نام Header، Token Prefix، محدودیت نرخ، صفحه‌بندی، Timezone و نمونه پاسخ واقعی را تحویل دهد. تا قبل از دریافت این موارد مسیر API ساخته یا حدس زده نمی‌شود.

### عملیات موردنیاز

| عملیات تجاری | انتظار از API |
|---|---|
| بررسی اتصال | اعتبارسنجی حساب و مجوزهای API |
| فهرست آزمون‌ها | شناسه خارجی، عنوان، درس/پایه، زمان و وضعیت |
| ایجاد آزمون | در صورت پشتیبانی؛ ساخت آزمون و بازگشت External Exam ID |
| جزئیات آزمون | بررسی مالکیت و وضعیت آزمون |
| دریافت نتایج | شناسه نتیجه، شناسه دانش‌آموز، نمره، نمره کل و زمان ثبت |
| ورود یکپارچه دانش‌آموز | تولید لینک/توکن کوتاه‌عمر برای ورود از شیخان به آزمون |
| Callback نتیجه | در صورت پشتیبانی؛ امضای Webhook و جلوگیری از Replay |

### قرارداد نرمال‌شده آزمون

خروجی API باید در Adapter به این مدل تبدیل شود:

\`\`\`json
{
  "external_exam_id": "QUIZ24-EXAM-ID",
  "title": "آزمون جامع ریاضی",
  "description": "توضیح آزمون",
  "starts_at": "2026-11-20T08:00:00Z",
  "ends_at": "2026-11-20T10:00:00Z",
  "status": "published"
}
\`\`\`

### قرارداد نرمال‌شده نتیجه

\`\`\`json
{
  "result_id": "QUIZ24-RESULT-ID",
  "student_identifier": "STUDENT-EXTERNAL-ID-OR-VERIFIED-PHONE",
  "student_name": "نام شرکت‌کننده",
  "score": 17.5,
  "max_score": 20,
  "submitted_at": "2026-11-20T09:35:00Z"
}
\`\`\`

موارد زیر باید از کارفرما تعیین تکلیف شود:

- شناسه قطعی برای تطبیق دانش‌آموز: کد دانش‌آموزی، موبایل تأییدشده یا شناسه‌ای که شیخان به Quiz24 می‌فرستد.
- آیا Quiz24 امکان ایجاد حساب/عضو یا فقط شرکت‌کننده مهمان دارد؟
- مقیاس نمره همیشه ۲۰ است یا هر آزمون \`max_score\` مستقل دارد؟
- آیا نتیجه بعد از ثبت قابل اصلاح است؟ چگونه نسخه جدید تشخیص داده می‌شود؟
- آزمون و نتیجه با Polling دریافت می‌شود یا Webhook؟
- صفحه‌بندی، ترتیب و فیلتر تاریخ نتایج چیست؟

### ورود یکپارچه (SSO)

در صورت پشتیبانی Quiz24، دانش‌آموز باید پس از ورود به شیخان بدون واردکردن گذرواژه دوم وارد آزمون شود. قرارداد لازم:

- شیخان یک شناسه پایدار دانش‌آموز را ارسال کند.
- سرویس Quiz24 یک Token/URL کوتاه‌عمر، یک‌بارمصرف و محدود به آزمون برگرداند.
- Token شامل اطلاعات حساس یا گذرواژه اصلی نباشد.
- \`return_url\` فقط از دامنه‌های مجاز باشد.
- زمان انقضا، امضا، Nonce و جلوگیری از Replay مشخص باشد.

تا زمان تأیید این قابلیت توسط Quiz24، هیچ فرم یا پیام رابط کاربری نباید «ورود یکپارچه فعال است» نمایش دهد.

## ۴. تطبیق نتایج و کارنامه

منطق داخلی Import در \`Quiz24ResultImporter\` است:

1. نتیجه با شناسه خارجی دانش‌آموز یا موبایل نرمال‌شده جستجو می‌شود.
2. نگاشت دستی قبلی در \`quiz24_student_mappings\` اولویت دارد.
3. نتیجه دانش‌آموز شناخته‌شده با کلید یکتای \`exam_id + student_id\` درج/به‌روزرسانی می‌شود؛ اجرای دوباره باعث رکورد تکراری نمی‌شود.
4. اگر شرکت‌کننده پیدا نشود، رکورد در \`quiz24_unmatched_participants\` ذخیره می‌شود و وارد کارنامه نمی‌شود.
5. مدیر یک شرکت‌کننده ناشناس را به یک دانش‌آموز فعال وصل می‌کند؛ نگاشت برای همگام‌سازی بعدی نگهداری می‌شود.
6. نمره منفی، نمره بیشتر از نمره کل، شناسه خالی یا ساختار ناقص رد می‌شود.
7. داده خام حساس نتیجه رمزنگاری‌شده نگهداری می‌شود.

نام دانش‌آموز به‌تنهایی معیار تطبیق خودکار نیست؛ دو دانش‌آموز ممکن است نام یکسان داشته باشند.

## ۵. وضعیت عملیات، تکرارپذیری و خطا

جدول \`integration_runs\` کارتابل عملیات خارجی است.

| وضعیت | معنی |
|---|---|
| \`waiting_contract\` | درخواست محلی ثبت شده؛ وب‌سرویس هنوز موجود/فعال نیست |
| \`queued\` | برای اجرا در صف قرار گرفته است |
| \`running\` | Adapter در حال اجرای درخواست است |
| \`succeeded\` | پاسخ معتبر سرویس دریافت و دیتابیس به‌روزرسانی شده است |
| \`failed\` | عملیات ناموفق بوده و علت خطا ثبت شده است |

تمام عملیات دارای \`correlation_id\` و \`idempotency_key\` هستند. هر درخواست صدور لایسنس، ساخت آزمون، ابطال یا همگام‌سازی باید در سمت ارائه‌دهنده نیز Idempotent باشد تا Retry موجب ساخت رکورد تکراری نشود.

### خطاها و Retry

| وضعیت HTTP | رفتار مورد انتظار |
|---|---|
| 400 / 422 | خطای داده؛ Retry خودکار نشود |
| 401 / 403 | خطای کلید یا مجوز؛ عملیات متوقف و هشدار مدیریتی ثبت شود |
| 404 | شناسه خارجی نامعتبر یا حذف‌شده؛ نیازمند اصلاح Mapping |
| 409 | تعارض/عملیات تکراری؛ وضعیت قبلی بررسی شود |
| 429 | رعایت \`Retry-After\` و Backoff |
| 5xx / Timeout | Retry محدود با Backoff و همان Idempotency Key |

فرمت خطای پیشنهادی:

\`\`\`json
{
  "error": {
    "code": "INVALID_COURSE",
    "message": "Provider-facing error message",
    "retryable": false,
    "details": {}
  },
  "request_id": "provider-request-id"
}
\`\`\`

### امنیت

- فقط HTTPS با اعتبارسنجی TLS.
- عدم ثبت API Key، Token، License Key یا URL دارای امضای موقت در Log.
- Tokenهای اتصال باید در Secret Manager یا فیلد encrypted دیتابیس نگهداری شوند.
- Webhookها باید امضای HMAC، Timestamp، Nonce و کنترل Replay داشته باشند.
- داده ارسالی Quiz24 حداقلی باشد و شناسه پایدار داخلی بر موبایل خام ترجیح داده شود.
- لینک ویدیو یا لایسنس نباید به مسیر عمومی Storage تبدیل شود.

## ۶. اقلامی که کارفرما باید تحویل دهد

1. مستند رسمی و نسخه API هر دو سرویس.
2. Base URL محیط Test و Production.
3. API Key/Token آزمایشی با مجوزهای موردنیاز.
4. نمونه واقعی Request/Response برای تمام عملیات جدول‌ها.
5. توضیح ایجاد دوره SpotPlayer: API دارد یا باید دوره دستی ساخته و ID آن ثبت شود؟
6. روش آپلود ویدیو، وضعیت پردازش و دریافت Video ID در SpotPlayer.
7. روش صدور، دریافت، ابطال و بررسی وضعیت لایسنس SpotPlayer.
8. روش دریافت فهرست آزمون‌ها و نتایج Quiz24.
9. روش SSO یا ایجاد Session آزمون برای دانش‌آموز.
10. شناسه مورد استفاده برای تطبیق دانش‌آموز و مقیاس نمره.
11. قرارداد Webhook یا محدودیت Polling، Rate Limit، Pagination و Retry.
12. Sandbox قابل تست و یک حساب/آزمون نمونه با داده غیرواقعی.

## ۷. معیار تحویل اتصال واقعی

اتصال زمانی Done محسوب می‌شود که تست‌های Sandbox زیر موفق باشند:

- بررسی اتصال با کلید معتبر و نامعتبر.
- ایجاد/نگاشت دوره و خواندن مجدد آن.
- ایجاد ویدیو و مشاهده وضعیت پردازش، در صورت پشتیبانی API.
- صدور یک لایسنس Test، دریافت وضعیت و ابطال آن.
- عدم صدور لایسنس برای دانش‌آموز فاقد Enrollment یا دوره منتشرنشده.
- دریافت آزمون Quiz24 و نگاشت External Exam ID.
- دریافت نتیجه، تطبیق دانش‌آموز و ثبت یکتا در کارنامه.
- نگهداری شرکت‌کننده ناشناس در صف مغایرت‌ها و اتصال دستی صحیح.
- اجرای دوباره هر عملیات بدون ایجاد رکورد خارجی/داخلی تکراری.
- ثبت خطا و Retry بدون افشای Token و License Key.

**تا قبل از تحویل اطلاعات بالا، وضعیت فعلی پروژه «آماده اتصال / منتظر قرارداد سرویس‌دهنده» است، نه «متصل و عملیاتی».**
